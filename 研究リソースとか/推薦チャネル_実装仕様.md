## 1. 何が変わるか

- 各波のフォロー経路の処理が終わったあと（`mem::swap` の前）に、推薦の処理を1段足した。
  - 推薦量 $B_s=\varepsilon\,\delta\,\varphi(\hat e_s/\bar e_0)\,p\sum_{i\in S_s}d_i$ を丸めた数 $n_s$ だけ、フォロー外へ届ける。
  - 宛先は**2ホップ先だけ**：「シェア者の出辺から1本を一様に選び、その先の後続を1人一様に選ぶ」2歩のウォーク（2026-10-28 に、全ノードから一様に選ぶ宛先と、その確率 $\theta$ を削除した）。
  - 受信済み（IP を含む）か行き止まりなら空振りとし、選び直さない。
- 推薦で届いた人は、フォロー経路と**同じ更新則**（`UserState::contact`）で受信する。シェアを決め、かつ後続を持てば次の波に入る。
- 反応率 $\hat e_s=(\bar H+k\,a_t)/(\bar C+k)$ は、そのラウンドでシェアを決めた人数 $\bar H$（フォロワー0人も含む）と受信した人数 $\bar C$ から計算する。推薦で届いた人も数える。IP は数えない。
- R3（アカウント記憶）：ラウンドを跨いで $a_{t+1}=\mu a_t+(1-\mu)\hat e^{\rm end}_t$ を持ち回す（$a_1=\bar e_0$）。
- 基準の反応率 $\bar e_0$ は、ユーザ状態集合（`us_id`）ごとに1回だけ計算する。

## 3. 設定（TOML）

表 `[recommender]` を足す。**表ごと省略すれば推薦なし**（既存の TOML はそのまま読める）。一部のキーだけ書けば、残りは既定値になる。綴りを間違えたキーはエラーにする。

| キー | 記号 | 既定値 | 範囲（`Config::validate`） |
| --- | --- | --- | --- |
| `eps` | $\varepsilon$（推薦の強さ） | 0（推薦なし） | $\ge0$ |
| `delta` | $\delta$（フォロー外の露出の割引、R4） | 1（割引なし） | $[0,1]$ |
| `tau` | $\tau$（しきい値） | 0（しきい値なし） | $\ge0$ |
| `phi_max` | $\varphi_{\max}$（倍率の上限） | 3 | $\ge\tau$ |
| `k` | $k$（擬似カウント） | 10 | $>0$ |
| `mu` | $\mu$（R3 の記憶の持続） | 1（記憶なし） | $[0,1]$ |

例：`test/config_rec.toml`（`test/config.toml` に `[recommender]` だけを足したもの）。

## 4. 出力

- parquet に2列を足した（全8列）：`mean_num_rec_rcvd`、`mean_num_xact_rec`（`f64`、推薦なしでは 0）。既存の6列の意味は変えていない。
- KV メタデータに `recommender`（`RecParams` の `Debug` 表記）を足した。`version_core` と `version_runner` は 0.3.0。新旧のファイルは、版と列の有無で見分けられる。

## 5. 乱数

- 推薦も、拡散と同じ系列ごとの `SmallRng` から引く。
- 引く順序（各波で、フォロー経路の辺ごとの乱数のあと）：
  1. 丸めの乱数1つ（$n_s$ を決める）
  2. 枠ごとに「出辺の選択（起点と1歩目を1回で）→ 2歩目」。1歩目の先が行き止まりなら2歩目は引かない
- 元資料 3.4節の「起点 → 1歩目」は、出辺を1回の乱数で選ぶことでまとめた（分布は同じ。起点を出次数に比例して選び、後続を一様に選ぶのと同値）。

## 8. 限界と注意

- **フォロワーのいない IP には推薦が付かない**：推薦量はシェア者の出次数の和に比例する。波0のシェア者は IP だけなので、IP のフォロワーが0人なら $B_0=0$ で、その後も広がらない（ENGB を `transposed = true` で読むと、出次数0の IP が選ばれることがある）。元資料の定義どおりの動きだが、結果を読むときは IP の出次数を確かめること。
- **推薦の効果は大きく出やすい**：congress（$p=0.1$）で $\varepsilon=1$ にすると、T = 3 ラウンド合計の外部行動数が、推薦なしの数倍から数十倍になった（ログ参照）。元資料 4.3節のとおり、臨界の近くかどうかを確かめてから読むこと。
- $\bar e_0=0$（平均的なメッセージで誰もシェアしない母集団）のときは、推薦しないことにした（仮定。$\hat e/\bar e_0$ が定義できないため）。
- clippy の「引数が多すぎる」警告が `diffuse_with_rec`（8）と `multiple_diffuse`（8）にも出る。`monte_carlo_average` には変更前から出ていたので、同じ扱いで残している。
- ビューア（`information_diffusion_veiwer`）の `core/` は、このリポジトリの古い版のコピーで、今回の変更は入っていない。ビューア側は `sim-api` に方式「Rモデル」として別に実装した（`information_diffusion_veiwer/recommender-v3-design.md`、2026-10-26）。乱数の流れが違うのでビット一致はしないが、`runner/examples/rec_crosscheck.rs` との突き合わせで統計的に一致することを確かめた（シェア・外部行動・推薦経由の受信の差は、いずれも合成標準誤差の 0.6 倍未満）。
